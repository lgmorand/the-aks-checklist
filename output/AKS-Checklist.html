BEFORE YOU BEGIN

A stronger baseline, not a rubber stamp.

Use this guide to make architecture decisions explicit. Select applicable checks, capture evidence, and assign owners to risks and exceptions. Completion is not a security certification or an application availability guarantee.

Guidance applies to AKS Automatic and Standard where supported. Validate your region, cloud, Kubernetes version, operating system, and feature support. Preview capabilities are not a production default. Always verify current Microsoft documentation before implementation.

Lifecycle watch / November 2026

Ingress migration is time-sensitive — Upstream Ingress NGINX maintenance ended in March 2026. AKS application routing NGINX critical-security-patch support runs through November 2026. Plan and test a supported Gateway API migration now.

Retired is not production-ready — Replace Azure Linux 2.0, Windows Server 2019, and the retired pod-managed identity add-on. Upgrade Basic Load Balancer and Availability Sets. Migrate kubenet before 31 March 2028.

How to use this guide

  1. Define business requirements, platform ownership, service objectives, and trust boundaries.
  2. Review every applicable check with the workload and platform teams.
  3. Record implementation evidence or a time-bound exception with an owner.
  4. Test failure, upgrade, and recovery paths; revisit the review after material changes.

Priority: High highlights foundational or time-sensitive controls; Medium covers important design and operational practices; Low is generally context-dependent. Priority is not a vulnerability severity rating.

Storage & data

6.01

Choose storage by durability, access mode, and performance

High

6.02

Size the nodes for storage needs

Medium

Each node size supports a maximum number of disks. Different node sizes also provide different amounts of local storage and network bandwidth. Plan for your application demands to deploy the appropriate size of nodes.

Different types and sizes of nodes are available. Each node (underlying VM) size provides a different amount of core resources such as CPU and memory. These VM sizes have a maximum number of disks that can be attached. Storage performance also varies between VM sizes for the maximum local and attached disk IOPS (input/output operations per second). If your applications require Azure Disks as their storage solution, plan for and choose an appropriate node VM size. The amount of CPU and memory isn't the only factor when you choose a VM size. The storage capabilities are also important.

6.05

Avoid keeping state in the cluster, and store data outside (AzStorage, AzSQL, Cosmos, etc)

High

Where possible, don't store service state inside the container. Instead, use an Azure platform as a service (PaaS) that supports multiregion replication.

Service state refers to the in-memory or on-disk data that a service requires to function. State includes the data structures and member variables that the service reads and writes. Depending on how the service is architected, the state might also include files or other resources that are stored on the disk. For example, the state might include the files a database uses to store data and transaction logs.

Enforce image vulnerability thresholds and exception expiry

Medium

Define policy using exploitability, exposure, severity, and available fixes. Block unacceptable risk, record owners and expiry for exceptions, and rescan continuously. An unfixed critical vulnerability is not automatically acceptable simply because the vendor has not published a fix.

READ MORE
  • Enforce image vulnerability thresholds and exception expiry
13.17

Validate container build and runtime policy

High

Validate approved base images, non-root execution where supported, exposed services, secret handling, and required labels. Apply rules based on the threat model; opening port 80 alone is not proof of noncompliance.

READ MORE
  • Validate container build and runtime policy
13.18

Assess application modernization before containerization

Low

Validate runtime support, licensing, state, external dependencies, health probes, and operational ownership before moving an application to AKS. Choose supported migration tooling based on the workload rather than assuming a point-and-containerize conversion produces a production-ready service.

READ MORE
  • Assess application modernization before containerization
13.19

Apply the right deployment type to your application

Low

There are a variety of techniques to deploy new applications to production so choosing the right strategy is an important decision that needs to be made to leverage the impact of change on the consumer.

READ MORE
  • Kubernetes Deployment Strategies
13.20

Use workload controllers instead of standalone pods

Low

Manage long-running applications through Deployments or StatefulSets, and finite work through Jobs or CronJobs. A standalone pod is not recreated after node loss by a workload controller; test replacement and application recovery.

READ MORE
  • Use workload controllers instead of standalone pods
13.21

Set image pull policy and deploy immutable image digests

Low

Use immutable digests for reproducible deployments and choose imagePullPolicy deliberately. Always checks registry resolution but can reuse cached layers; IfNotPresent reuses cached images. Do not rely on mutable latest tags, and test registry failure behavior.

READ MORE
  • Set image pull policy and deploy immutable image digests
13.22

Provision Azure resources with reviewed infrastructure as code

Medium

Use Bicep, ARM templates, or Terraform modules with pinned versions, environment-specific configuration, least-privilege deployment identities, and reviewed changes. Keep state protected, detect drift, and rehearse rebuilding the platform.

READ MORE
  • Provision Azure resources with reviewed infrastructure as code
13.23

Use canary or blue/green deployments

Medium

This will help ensure your workloads remain online during cluster upgrades.

READ MORE
  • Blue-green deployment for AKS
13.24

Evaluate Dapr only when its application capabilities are needed

Low

Dapr can provide service invocation, pub/sub, state management, and other distributed application APIs. Adopt it when those capabilities justify additional sidecars, control-plane components, security configuration, and lifecycle management; it is not an upgrade-availability mechanism.

READ MORE
  • Evaluate Dapr only when its application capabilities are needed
13.25

Validate deprecated Kubernetes APIs before every upgrade

High

Check release notes, API-server warnings, manifests, CRDs, Helm charts, operators, and admission webhooks for APIs removed in the target version. Upgrade dependencies first and test conversion and rollback paths in a representative environment.

READ MORE
  • Validate deprecated Kubernetes APIs before every upgrade
13.26

Secure CI/CD with federation and scoped deployment permissions

High

Use OIDC federation from the CI platform to Azure, protect release environments, pin reviewed actions and build dependencies, and scope deployment identities to the required namespaces and resources. Keep production credentials and kubeconfig files out of logs and artifacts.

Images & supply chain

Build, verify, patch, and distribute trusted container artifacts.

14.01

Scan the container image against vulnerabilities

High

Scan operating-system packages and application dependencies in container images during build and continuously after publication. Triage findings using exploitability and exposure, enforce remediation targets, and verify deployed image digests. A clean scan does not prove that an image is free of vulnerabilities.

Allow deploying containers only from known registries

Medium

14.03

Detect and respond to container runtime threats

High

Enable supported runtime threat detection, such as Microsoft Defender for Containers, and route alerts into incident response. Validate required sensors and permissions, investigate suspicious process and network activity, and rehearse containment without assuming a sensor prevents every attack.

READ MORE
  • Runtime threat protection
14.04

Prevent promotion of images that violate current policy

High

Continuously rescan stored images and block release promotion or admission when they violate approved risk policy. Verify that quarantine tooling is supported and enforced by every pull path; a registry scan alone does not block deployment.

READ MORE
  • Prevent promotion of images that violate current policy
14.05

Scope registry roles to the required repositories and actions

High

Separate image push, pull, delete, signing, and administrative permissions. For ABAC-enabled registries, use supported repository roles and conditions rather than assuming AcrPull/AcrPush applies. Audit assignments and keep the registry admin user disabled.

READ MORE
  • Scope registry roles to the required repositories and actions
14.06

Network Segmentation of Docker Registries

High

Limit access to a registry by assigning virtual network private IP addresses to the registry endpoints and using Azure Private Link. Network traffic between the clients on the virtual network and the registry's private endpoints traverses the virtual network and a private link on the Microsoft backbone network, eliminating exposure from the public internet. Private Link also enables enables private registry access from on-premises through Azure ExpressRoute private peering or a VPN gateway.

READ MORE
  • Azure Container Registry Private Link
14.07

Use minimal, maintained base images

Medium

Choose supported, regularly patched minimal or distroless images compatible with the application. Do not use end-of-life Debian 10 examples. Removing a shell reduces attack surface but does not prevent exploitation; retain a controlled debug workflow.

READ MORE
  • Use minimal, maintained base images
14.08

Refresh container when base image is updated

Low

As you use base images for application images, use automation to build new images when the base image is updated. As those base images typically include security fixes, update any downstream application container images.

14.09

Generate SBOMs and verify artifact provenance

High

Generate an SBOM for each release, retain build provenance, and sign immutable artifacts using supported OCI signing tools. Verify signatures and trusted identities during release or admission; signing without verification does not establish a supply-chain control.

Retain and replicate the artifacts required for recovery

Medium

Keep known-good image digests, Helm charts, manifests, and signatures available for the recovery window. Test pulls from the recovery region, registry private DNS, retention rules, and access identities; avoid deleting an image still referenced by production or rollback plans.

Cost & sustainability

Measure unit costs and balance efficiency with reliability and operational effort.

15.01

Allocate costs to teams and workloads

High

Use AKS cost analysis where supported or a maintained allocation tool. Combine Azure tags and Kubernetes labels with ownership, budgets, and chargeback rules. Include idle capacity, monitoring ingestion, network egress, storage, licenses, and managed add-ons.

READ MORE
  • Allocate costs to teams and workloads
15.02

Right-size from measured demand and unit economics

Medium

Review requests, limits, node utilization, autoscaler behavior, and cost per business transaction. Reduce waste without removing failure headroom, disrupting latency objectives, or creating unschedulable workloads.

READ MORE
  • Right-size from measured demand and unit economics
15.03

Use reservations and savings plans only for stable baseline demand

Medium

Model measured compute commitments against expected VM families, regions, and utilization. Use Spot capacity only for interruption-tolerant workloads with checkpointing and fallback; never rely on Spot for essential system components.

READ MORE
  • Use reservations and savings plans only for stable baseline demand
15.04

Stop disposable environments and clean orphaned resources safely

Medium

Schedule nonproduction shutdown or scale-down when supported and acceptable. Review unused disks, public IPs, snapshots, images, and workspaces with owners and retention policies before deletion; never treat an unattached disk as automatically disposable.

READ MORE
  • Stop disposable environments and clean orphaned resources safely
15.05

Evaluate sustainability without compromising service objectives

Low

Measure utilization and workload efficiency, evaluate compatible Arm64 compute, and select regions within latency and residency constraints. Consider the total operational footprint rather than assuming one VM architecture is always cheaper or lower-carbon.
